# План UI для Stateful Objects в Firewall (RU)

Документ объясняет простыми словами, что такое `ct helper/timeout/expectation`, `limit/quota/counter`, зачем они нужны, и как именно это должно выглядеть в UI.

---

## 1) Что это за объекты и зачем они нужны

`Stateful Objects` — это переиспользуемые сущности nftables, которые создаются один раз, а потом подключаются в правилах.

1. `counter`
- Что делает: считает пакеты и байты по правилу.
- Зачем: видеть реальную нагрузку/трафик.

2. `limit`
- Что делает: ограничивает скорость срабатывания правила (например, не более 20 пакетов/сек).
- Зачем: защита от флуда/брутфорса.

3. `quota`
- Что делает: ограничивает общий объём трафика (например, 10 GB), после исчерпания правило перестаёт матчиться.
- Зачем: лимиты трафика, временные окна доступа.

4. `ct helper`
- Что делает: подключает conntrack-helper для специфических протоколов (FTP/SIP и т.п.).
- Зачем: корректный разбор сложных протоколов с несколькими потоками.

5. `ct timeout`
- Что делает: задаёт профиль таймаутов conntrack по типу протокола/состояний.
- Зачем: тонкая настройка времени жизни соединений.

6. `ct expectation`
- Что делает: заранее описывает ожидаемое дочернее соединение (related flow).
- Зачем: сложные сценарии с динамическими потоками (редко, для advanced).

7. `flowtable`
- Что делает: ускоряет forwarding path для fastpath-сценариев.
- Зачем: производительность на высоких скоростях.

---

## 2) Где это будет в интерфейсе

Раздел `Firewall -> Policy`.

На верхнем уровне вкладок:
- `policy`
- `collections`
- `objects` (новая)
- `table builder`

Во вкладке `objects`:
- единая таблица объектов;
- фильтр по типу: `counter | limit | quota | ct helper | ct timeout | ct expectation | flowtable`;
- кнопки: `Add`, `Del`, `Disable`, `Enable`, `Columns`.

Почему единая таблица:
- одинаковый CRUD-поток;
- проще тестировать;
- меньше дублирования UI.

---

## 3) Как выглядит создание (кнопка и окно)

### 3.1 Кнопка

Кнопка `+ Add` во вкладке `objects` открывает модальное окно `Add Object`.

### 3.2 Модальное окно `Add Object`

Общие поля (для всех типов):
- `Enabled` (toggle)
- `Family` (`inet/ip/ip6/bridge/netdev`, по умолчанию из текущего контекста)
- `Table` (select)
- `Name` (уникальное имя)
- `Comment` (опционально)
- `Type` (select: один из 7 типов)

Ниже показывается динамический блок полей по выбранному `Type`.

## 4) Поля по каждому типу (что вводим и что получаем)

### 4.1 `counter`

Поля:
- `Counter mode`: `packets+bytes` (по умолчанию)

Эффект:
- правило, ссылающееся на этот object, считает трафик.

### 4.2 `limit`

Поля:
- `Rate` (число)
- `Per` (`second/minute/hour/day`)
- `Burst` (опционально)
- `Over` (toggle: матчить превышение вместо нормы)

Эффект:
- контроль частоты срабатываний правила.

### 4.3 `quota`

Поля:
- `Size` (число)
- `Unit` (`B/KB/MB/GB`)
- `Used` (readonly при редактировании)
- `Over` (toggle)

Эффект:
- правило действует, пока не исчерпан заданный объём.

### 4.4 `ct helper`

Поля:
- `L4 protocol` (`tcp/udp`)
- `Helper name` (например `ftp`)

Эффект:
- conntrack использует helper для указанных flow.

### 4.5 `ct timeout`

Поля:
- `L4 protocol` (`tcp/udp`)
- `State timeouts` (набор полей по состояниям, например `established`, `close_wait`, `time_wait`)

Эффект:
- переопределяет таймауты conntrack-потоков.

### 4.6 `ct expectation`

Поля:
- `L4 protocol`
- `Timeout`
- `DPort`/`Sport` (по необходимости)
- `Size` (если требуется профилем)

Эффект:
- описывает ожидаемое related-соединение.

### 4.7 `flowtable`

Поля:
- `Hook` (`ingress`)
- `Priority`
- `Devices` (multi-select интерфейсов)

Эффект:
- ускоренный forwarding для выбранных интерфейсов/цепочек.

---

## 5) Как это подключается в Add Rule

В `Add Firewall Rule` добавляется блок `Stateful objects` (в `Advanced match`/`Action`, по типу объекта):

1. Toggle `Use object`.
2. Поле `Object type` (например `limit`).
3. Поле `Object reference` (dropdown существующих объектов этого типа в текущем family/table).

Принцип:
- в правиле не вводим “сырые строки” руками;
- выбираем только существующий объект из списка.

---

## 6) Валидации (чтобы не ломать apply)

1. Имя объекта уникально в пределах `family + table + type`.
2. Нельзя удалить объект, если на него есть ссылки в правилах.
3. Нельзя выбрать объект из другой таблицы/семейства.
4. Для `flowtable` валидировать `hook/priority/devices`.
5. Для `ct*` объектов выдавать явную ошибку, если контекст таблицы/chain не поддерживается.

---

## 7) Что пользователь увидит в таблице Objects

Рекомендуемые колонки:
- `type`
- `name`
- `family`
- `table`
- `summary` (кратко: `rate 20/s burst 40`, `10GB`, `tcp helper ftp`)
- `comment`
- `status` (`enabled/disabled`)
- `refs` (сколько правил ссылаются)

Двойной клик по строке:
- открывает `Edit Object` (тот же layout, что `Add Object`).

---

## 8) План внедрения по шагам

### Шаг 1 (быстрый)
- Вкладка `objects` + CRUD для `counter/limit/quota`.
- Подключение этих трёх типов в `Add Rule`.

### Шаг 2 (средний)
- CRUD для `ct helper/ct timeout`.
- Подключение в `Add Rule` через reference.

### Шаг 3 (advanced)
- `ct expectation` и `flowtable`.
- Расширенные валидации + e2e negative/edge кейсы.

---

## 9) Почему это полезно именно для трафика

1. `counter` даёт наблюдаемость (сколько реально ходит трафика).
2. `limit/quota` дают контроль и защиту от перегрузки.
3. `ct*` объекты улучшают поведение сложных протоколов и stateful-логики.
4. `flowtable` даёт рост производительности на потоке.

Итог:
- меньше ручных ошибок;
- предсказуемое поведение правил;
- проще сопровождать и тестировать.

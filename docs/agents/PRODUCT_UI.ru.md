# Принципы продуктового UI AWG Manager

## Назначение

Документ фиксирует устойчивые правила интерфейса. Он не описывает конкретный
экран и не заменяет задание.

Основной пользователь — сетевой администратор, которому важно быстро понять:

- текущее состояние;
- что изменится после действия;
- сохранена ли конфигурация;
- применена ли она к runtime;
- как отменить или исправить ошибку.

## 1. Согласованность важнее оригинальности

Для новой функции сначала найти ближайший существующий экран:

- Interfaces;
- Clients;
- Firewall;
- IPsec.

Повторять его:

- ширину и структуру контента;
- тип заголовка;
- расположение основной кнопки;
- таблицы, карточки, диалоги и sheet;
- loading, empty, error и success состояния;
- терминологию.

Не изобретать новый паттерн только потому, что он выглядит современнее.

## 2. Навигация

- Не менять общий sidebar ради одной задачи.
- Не создавать новый верхнеуровневый раздел без явного решения владельца.
- Название пункта должно описывать объект или функцию, а не внутреннюю
  технологию реализации.
- Для небольшого модуля предпочтительнее один экран, а не несколько вложенных
  уровней.
- Активный раздел и заголовок страницы должны совпадать по смыслу.

## 3. Иерархия экрана

Рекомендуемый порядок:

1. название и короткое состояние;
2. основное содержимое: таблица или форма;
3. одна основная кнопка;
4. вторичные действия;
5. редкие настройки в `Advanced`;
6. предупреждения рядом с опасным действием.

Не размещать несколько равноправных primary-кнопок.

## 4. Формы

- Метка поля должна быть понятна без чтения backend-кода.
- Placeholder не заменяет label.
- Короткая подсказка нужна только там, где сетевой инженер может трактовать поле
  неоднозначно.
- Значение по умолчанию должно быть безопасным.
- Не очищать заполненную форму после ошибки сохранения.
- Валидация должна объяснять, что исправить.
- Не показывать внутренние ID, storage paths и runtime-команды без
  пользовательской необходимости.

## 5. Save и Apply

Это критическое правило AWG Manager:

- `Save` — записывает желаемую конфигурацию в storage.
- `Apply` — меняет runtime/состояние ОС.
- Если одно действие делает оба шага, UI и API должны говорить об этом явно.
- Если модуль пока работает только через storage, нельзя показывать успешное
  применение к системе.
- После действия пользователь должен видеть новое состояние и понятный итог.

## 6. Таблицы и коллекции

- Основные столбцы видны сразу.
- Редкие технические данные не перегружают таблицу.
- Действия строки находятся в одном привычном месте.
- Empty state объясняет, что создать и зачем.
- Удаление требует подтверждения, если восстановление неочевидно.
- Добавление объекта не должно заставлять пользователя повторно вводить данные
  после серверной ошибки.

## 7. Состояния

Каждый новый экран обязан иметь:

- loading;
- empty;
- loaded;
- validation error;
- API error;
- saving/applying;
- success;
- disabled/unsupported, если функция недоступна на стенде.

Нельзя оставлять кнопку активной при уже выполняющемся запросе.

## 8. Что агент решает сам

Агент не спрашивает владельца о:

- стандартных отступах;
- обычном расположении label;
- обработке loading/error;
- повторном использовании существующего компонента;
- очевидной валидации;
- соответствии уже существующему экрану.

Перед передачей агент исправляет такие вещи самостоятельно.

## 9. Что выносится владельцу

Только субъективные продуктовые решения, например:

- какой из двух вариантов расположения лучше;
- какое пользовательское название понятнее;
- нужен ли параметр на основном экране или в `Advanced`;
- должен ли модуль быть отдельным пунктом sidebar;
- является ли конкретная плотность интерфейса визуально удобной.

В финальном отчёте — максимум три вопроса, каждый в формате:

```text
Место:
Вариант/проблема:
Рекомендация агента:
Что нужно решить владельцу:
```

## 10. Критерий готовности UI

Экран готов к показу владельцу, когда агент уже проверил:

- функциональный сценарий;
- соответствие API;
- ошибки браузерной консоли;
- loading/error/success;
- адаптацию к текущей ширине приложения;
- согласованность с ближайшим существующим экраном.

Владелец оценивает вкус и направление продукта, а не заменяет QA.

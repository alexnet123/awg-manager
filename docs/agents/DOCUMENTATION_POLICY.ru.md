# Политика документации AWG Manager

## Цель

Документация должна помогать найти один актуальный ответ, а не сохранять каждый
промежуточный ход агента.

## 1. Категории

После постепенной миграции используются категории:

```text
docs/
├── README.md
├── agents/       # короткие постоянные правила для агентов
├── development/  # архитектура, ownership, onboarding; RU + EN
├── user/         # руководство пользователя
├── reference/    # API и внешние технические справочники
├── testing/      # устойчивые тестовые методики и release gates
├── operations/   # deploy, стенды, эксплуатация
└── archive/      # завершённые планы и исторические материалы
```

## 2. Один источник истины

Для каждой темы должен быть один канонический документ.

Перед созданием `.md` агент обязан:

1. выполнить поиск по `docs`;
2. открыть `docs/README.md`;
3. определить, можно ли обновить существующий документ;
4. проверить, будет ли новый документ полезен через шесть месяцев.

Если ответ можно добавить в существующий документ — новый файл запрещён.

## 3. Что не является постоянной документацией

Следующее хранится в Issue, PR/MR, чате агента или локальном `tasks/active`:

- план конкретной задачи;
- todo;
- список текущих багов;
- progress;
- отчёт агента;
- результаты одного запуска тестов;
- варианты, которые ещё не приняты;
- временная инвентаризация;
- заметки исследования.

Git уже хранит историю изменений. Не нужно дублировать её отдельными отчётами.

## 4. Запреты для агентов

Без явного требования запрещено создавать файлы с суффиксами:

```text
_PLAN
_REPORT
_NOTES
_BUGLIST
_PROGRESS
_FINAL
_FINAL2
_NEW
_UPDATED
_V2
```

Дата в имени допустима только для действительно временного архивного снимка,
который помещается в `docs/archive/`.

Нельзя создавать отдельные документы «backend», «frontend», «API», «UI» для
одной маленькой функции, если они описывают один пользовательский модуль.

## 5. Пользовательская документация

User guide отвечает на вопросы:

- зачем нужна функция;
- где её найти;
- что означают поля;
- как выполнить типовой сценарий;
- какой результат ожидать;
- что делать при типовой ошибке;
- какие есть ограничения.

User guide не описывает:

- Python-классы;
- внутренние JSON-файлы;
- router/service/repository;
- diff задачи;
- историю реализации;
- полный API-контракт.

Использовать `docs/user/GUIDE_TEMPLATE.ru.md`.

## 6. Development documentation

`docs/development/` — источник истины по архитектуре и ownership.

При изменении ответственности:

- обновить `MODULE_MAP.md`;
- обновить `MODULE_MAP.ru.md`;
- сохранить одинаковый смысл в обеих версиях.

Не создавать ещё один `ARCHITECTURE.md`, если информация принадлежит module map.

## 7. API/reference

Полный wire-контракт хранится в одном API reference.

User guide может упомянуть, что функция доступна через API, но не копирует весь
контракт. Иначе версии быстро расходятся.

Большие внешние справочники не должны попадать в обязательный контекст агента.
Открывать их только по задаче.

## 8. Новый документ

Новый постоянный `.md` допустим, если одновременно выполняются условия:

- тема самостоятельна;
- нет канонического документа;
- документ будет поддерживаться;
- указан владелец/категория;
- добавлена ссылка в `docs/README.md`;
- в задании явно указано его создание или агент обосновал необходимость в PR.

## 9. Удаление и архив

Не удалять старые документы во время feature-задачи.

Для уборки делать отдельный docs-only PR:

1. составить mapping старый путь → новый путь;
2. переместить без одновременного переписывания содержания;
3. обновить ссылки;
4. проверить поиск по старым путям;
5. только затем объединять/удалять дубли.

Завершённые планы архивируются, а не остаются рядом с актуальным user/API guide.

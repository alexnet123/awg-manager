# Стандарт добавления функции или модуля

## 1. Выбор ближайшего аналога

Перед кодом определить, какой текущий домен ближе.

### AWG (`backend/domains/awg`)

Использовать как аналог, когда задача связана с:

- интерфейсами или клиентами;
- основной SQLite-моделью;
- конфигурациями AWG;
- существующим runtime AWG.

### Firewall (`backend/domains/firewall`)

Использовать как аналог, когда задача включает:

- отдельную хранимую конфигурацию;
- валидацию сложной схемы;
- генерацию/применение runtime-конфигурации;
- разделение service, repository/store и runtime adapter.

### IPsec (`backend/domains/ipsec`)

Использовать как аналог, когда задача включает:

- коллекции конфигурационных объектов;
- JSON/storage;
- отдельные операции apply/start/stop/status;
- отдельный экран управления системой.

Нельзя копировать модуль целиком. Нужно повторять границы и паттерны, а не
случайные детали.

## 2. Решения до кодирования

Задание должно отвечать на вопросы:

1. Что является сохранённой желаемой конфигурацией?
2. Где она хранится?
3. Что является runtime-состоянием?
4. Выполняет ли Save только storage или также Apply?
5. Какие endpoints добавляются?
6. Где находится UI?
7. Какой существующий экран является визуальным аналогом?
8. Какие тесты подтверждают готовность?
9. Какой канонический документ обновляется?
10. Какие вещи точно не входят в задачу?

Если задача не отвечает на runtime-вопрос, безопасное значение по умолчанию:
**реализовать storage, API и UI без скрытого изменения ОС**.

## 3. Backend-шаблон

Новый самостоятельный домен:

```text
backend/domains/<domain>/
├── __init__.py
├── service.py
├── store.py или repository.py
├── validation_ops.py
├── schema.py                 # только если схема нетривиальна
└── runtime_adapter.py        # только если есть side effects ОС
```

Правила:

- HTTP request/response не попадают в домен.
- Router разбирает метод и путь, вызывает service, формирует wire response.
- Store/repository отвечает только за persistence.
- Validation нормализует и проверяет вход.
- Runtime adapter является единственным местом внешних команд/side effects
  данного домена.
- Service оркестрирует доменные операции.
- Домен не импортирует другой домен.
- Общий helper переносится в `backend/common` только после реального повторного
  использования.

Маленькому модулю не нужно искусственно создавать все файлы. Допустимо начать с
`service.py` + `store.py`, если обязанности остаются ясными.

## 4. API-шаблон

AWG Manager использует endpoints от корня приложения, например `/interfaces`,
`/clients`, `/firewall`. Для нового модуля использовать тот же стиль:

```text
GET /<domain>
PUT /<domain>
POST /<domain>/<action>       # только для явного runtime-действия
```

Не добавлять префикс `/api`, если отдельная задача не меняет весь контракт.

Обязательные свойства:

- аутентификация через текущий `X-API-Key`;
- стабильная JSON-форма;
- понятные 4xx для валидации;
- 5xx не раскрывает секреты и внутренние команды;
- повторное чтение после сохранения возвращает нормализованные данные;
- Save и Apply разделены на уровне endpoint, если эффекты различаются.

При изменении API обновить `docs/API.md` или его будущее каноническое место.

## 5. Frontend-шаблон

```text
webui/src/frontend/domains/<domain>/api.ts
webui/src/pages/<domain>.tsx
webui/src/pages/<domain>/*    # только если экран стал сложным
webui/tests/<domain>.spec.ts
```

Изменять `webui/src/App.tsx` только для минимального подключения маршрута/пункта
навигации, одобренного задачей.

Правила:

- API details не размазывать по компонентам;
- использовать текущий auth/API client pattern;
- переиспользовать `webui/src/components/ui`;
- не менять общую тему;
- реализовать loading, empty, error, saving и success;
- после изменения выполнить `npm run build`;
- обновить `webui/dist`.

## 6. Тестовый минимум

Backend:

- unit-тест storage/repository;
- unit-тест validation/service;
- API contract для новых endpoints;
- полный `python3 -m pytest -q tests`.

Frontend:

- production build;
- Playwright happy path;
- Playwright validation/error path, если он критичен;
- проверка отсутствия console errors.

Runtime:

- runtime-тест только если задача действительно включает Apply/Start/Stop;
- storage-only модуль не должен имитировать успешный runtime apply.

## 7. Документация

Для обычной функции обновлять только:

- API reference, если меняется API;
- один пользовательский guide, если появляется пользовательское поведение;
- RU/EN module map, если меняется владение кодом.

Не создавать:

- отдельный design doc;
- implementation plan;
- progress report;
- тестовый отчёт;
- «как я реализовал»;
- копию API в user guide.

## 8. Передача результата

Агент возвращает результат по `tasks/RESULT_TEMPLATE.md`.

Особенно важно:

```text
Что должен оценить владелец продукта:
1. ...
2. ...
3. ...
```

Этот блок может быть пустым. Не нужно придумывать вопросы ради отчёта.
